Backend 1 Apache Kafka

Where in your story: event backbone of the orchestration platform — payment orchestration events, notification dispatch (email/SMS), audit trail. Multiple consumer services read the same events.

Core answers

  • Why Kafka over RabbitMQ: pull-based log with retention → consumers can replay history (audit/recovery), much higher throughput, multiple independent consumer groups on the same topic. RabbitMQ = per-message routing/ack queues; Kafka = distributed append-only log.
  • Delivery semantics: default is at-least-once. We make processing effectively-once by (1) idempotent producer (enable.idempotence=true, acks=all, min.insync.replicas=2), (2) idempotent consumers — dedupe by event_id in Redis/DB table.
  • Ordering: guaranteed only within a partition. We key messages by transactionId/accountId, so all events for one entity are ordered; global ordering isn't needed.
  • Error handling (they WILL ask): Spring Kafka @RetryableTopic — non-blocking retries with exponential backoff on retry topics → after N attempts, publish to DLT (dead-letter topic); alerting to Grafana, ops dashboard for DLT triage.
  • Offset management: manual ack after successful processing; commit = checkpoint. Poison pill → seek past + record, never block the partition.
  • Rebalance: group rebalances when a member dies; tune max.poll.interval.ms so slow batches don't trigger rebalance storms; cooperative-sticky assignor for smoother handover.
Senior kill-shot — Transactional Outbox pattern.
Problem: dual-write — commit DB tx then publish to Kafka and the publish fails (or vice versa) → inconsistency.
Solution: write the event to an outbox table inside the same DB transaction as the business change; a relay (or Debezium CDC) publishes it to Kafka. Kafka publish is never inside the DB transaction. Deploy this answer whenever they ask about DB↔Kafka consistency.
Trap: "Is Kafka exactly-once?"

Transactional producer gives EOS for Kafka→Kafka consume-transform-produce flows. For side-effectful consumers (send SMS, write external API) you still dedupe: at-least-once delivery + idempotent processing.

Trap: "Consumer lag spikes at peak — what do you do?"

Increase partitions + listener concurrency, batch listeners, monitor lag with an exporter → Grafana alert before it hurts SLA.

Backend 2 Elasticsearch

Where in your story: centralized logging for all microservices (Grafana dashboards on top) + transaction search module.

Core answers

  • Why not SQL LIKE '%x%': leading wildcard = full table scan, no index. ES uses an inverted index (token → list of documents) built at index time → fast full-text + filters.
  • Our pipeline: services log structured JSON with trace_id → Filebeat → Logstash (parse/enrich) → ES → Grafana/Kibana. Trace ID correlates one request across gateway → services → Kafka consumers.
  • NRT: searchable after ~1s refresh interval; durability comes from translog + flush, not refresh.
  • Cluster basics: data nodes hold shards; index = primary shards + replicas (HA + read throughput); explicit mapping in prod — a wrong text vs keyword mapping ruins aggregations. keyword = exact/filter/agg, text = full-text with analyzer.
  • Ops we did: ILM policy — rollover daily alias, delete after 30 days; shard sizing ~30–50GB max; yellow cluster = replicas unassigned.
  • Zero-downtime mapping change: reindex into a new index behind an alias, swap the alias when done.
Trap: "Is ES a primary datastore?"

No: no joins/ACID across documents, eventual consistency. PostgreSQL stays the source of truth; ES is a search/projection.

Trap: "Filter vs query context?"

Filter context is non-scoring and cacheable — put exact conditions (status, date range) in filter; only relevance terms in must.

Backend 3 Spring Batch

Where in your story: nightly reconciliation (bank statements vs internal ledger), monthly compliance reports, partner data sync, backup validation — millions of records.

Core answers

  • Chunk-oriented model: read items → process → write per chunk; each chunk = its own transaction (commit-interval). ItemReader → ItemProcessor → ItemWriter.
  • Metadata tables: JobRepository persists JOB_INSTANCE / JOB_EXECUTION / STEP_EXECUTION in the DB → restartable: a failed job restarts from its checkpoint (ExecutionContext), and a completed instance with the same params won't rerun (idempotent scheduling).
  • Fault tolerance: skip (SkipPolicy + skip-limit; bad rows → SkipListener logs them to a dead-letter table) and retry (retry-limit, e.g. transient partner API errors):
    faultTolerant().skip(FlatFileParseException.class).skipLimit(100).retry(DeadlockLoserDataAccessException.class).retryLimit(3)
  • Scaling: multi-threaded step (simple); partitioning — manager splits by date range into worker steps (our default for reconciliation); remote partitioning via Kafka for very big loads.
  • Tuning: chunk size 500–1000, page size on readers, never load all in memory; listeners push duration/skip-count metrics to Grafana.
  • Scheduling: Spring @Scheduled / Quartz + a distributed lock (ShedLock/DB lock) so only one node runs the job in a multi-pod deployment.
Trap: "Chunk transaction fails at item 990 — what happens?"

The whole chunk rolls back. With skip configured, Spring re-reads the chunk item-by-item and skips only the offender — that's why skip + restart semantics matter.

Trap: "Is JdbcCursorItemReader restartable?"

Cursor readers aren't transactional-restartable by themselves — use paging readers or the process-indicator pattern (mark rows processed) for restartability.

Backend 4 @Transactional in Spring

Where in your story: anywhere money moves — orchestration sagas, payment records, audit logs.

Core answers

  • How it works: Spring AOP wraps the bean in a proxy; the proxy begins/commits/rolls back the tx around public method calls. JDK dynamic proxy (interface) or CGLIB (subclass).
  • Rollback rules (classic question): default rolls back on RuntimeException and Error only — checked exceptions do NOT roll back unless rollbackFor = Exception.class. We set it explicitly on money-path methods.
  • Propagation:
    • REQUIRED (default) — join existing or create new.
    • REQUIRES_NEW — suspends outer tx, independent commit/rollback. Our use: the audit log of a failed attempt must persist even when the main payment tx rolls back.
    • NESTED — savepoint within the same tx (JDBC only).
    • MANDATORY / NEVER / SUPPORTS / NOT_SUPPORTED — know the names.
  • Isolation: PostgreSQL default = READ_COMMITTED, MySQL InnoDB = REPEATABLE_READ; phenomena: dirty / non-repeatable / phantom read. In practice: optimistic locking with @Version; pessimistic (SELECT ... FOR UPDATE) only for hot contention.
  • The two classic bugs:
    1. Self-invocation: this.method2() inside the same bean bypasses the proxy → no new transaction. Fix: move it to another bean (or self-injection).
    2. @Transactional on private/final methods doesn't work (proxy can't intercept/override).
  • Keep transactions short: never call Kafka/HTTP/SMTP inside a DB tx → connection-pool exhaustion + dual-write problem → outbox pattern (links back to Kafka — sounds great).
  • readOnly = true for report/query methods: Hibernate skips dirty-checking (flush MANUAL), driver hint to DB.
Trap: "Outer REQUIRED + inner REQUIRES_NEW; inner rolls back — what does outer see?"

Inner is independent: it rolled back, its resources released. Outer continues and can still commit — unless the inner exception propagates out and hits outer's rollback rule.

Trap: "How do you test transactions?"

@DataJpaTest is transactional-rollback by default — REQUIRES_NEW is invisible inside it. Test real commits with Testcontainers.

Backend 5 Exception handling in REST APIs

Where in your story: platform-wide error contract used by web + mobile + partner clients.

Core answers

  • Central handler: @RestControllerAdvice + @ExceptionHandler(SomeException.class) returning a consistent envelope. Local handlers only as rare exception.
  • Custom hierarchy: base ApiException(code, message) → NotFoundException (404), ValidationException (400), ConflictException (409), ExternalServiceException (502), AuthException (401/403). ErrorCode enum = stable machine-readable code (PAY-4021) so clients branch on it.
  • Validation: @Valid + Bean Validation on DTOs; catch MethodArgumentNotValidException globally → 400 with per-field field, message list.
  • Error body shape: timestamp, status, code, message, path, traceId — traceId jumps straight to the logs in ELK. Never leak stack traces or SQL messages.
  • Modern note: Spring 6 supports RFC 7807 Problem Details (ProblemDetail) — say you know it even if you keep a custom envelope for legacy clients.
  • Log once, in the advice (warn for 4xx, error for 5xx) with MDC traceId — not scattered catch blocks.
  • Same discipline elsewhere: Kafka listeners use a listener error handler → DLT; WebClient/RestClient onStatus maps partner errors to ExternalServiceException.
Trap: "Two @ControllerAdvice with overlapping handlers — order?"

@Order decides; the more specific advice should win.

Trap: "Exception thrown in a filter — does the advice catch it?"

No — advice only covers controllers. Handle it inside the filter (try/catch + error response) or via a custom ErrorController.

Backend 6 Spring Cloud

Where in your story: the microservices layer — but be smart: you run on Kubernetes, so tell the modern version.

Core answers (your stack)

  • API Gateway — Spring Cloud Gateway: single edge for all clients — routing, JWT validation at the edge, rate limiting (Redis RequestRateLimiter filter) per client/API key, retry + timeout filters, centralized CORS.
  • Service discovery: on K8s we do not run Eureka — K8s Services + DNS is the registry (platform-native, one less stateful system; Eureka/Consul for VM/on-prem).
  • Circuit breaking — Resilience4j (Hystrix is dead — say that): CircuitBreaker + TimeLimiter + Retry around partner/banking integrations with fallbacks (return last-known status / queue for retry). Sliding-window ratio opens the breaker; half-open probes recovery. Also Project 2: retry + circuit breaker on REST/SOAP integrations.
  • Config: Spring Cloud Config Server for externalized config (on-prem variant); in K8s → ConfigMaps + Secrets. Modern Spring Cloud dropped bootstrap.yml → spring.config.import.
  • Load balancing: Spring Cloud LoadBalancer (replaced Ribbon) for client-side balancing to non-K8s services.
  • Distributed tracing: Micrometer Tracing (ex-Sleuth) + Zipkin/Tempo — traceId propagated gateway → service → Kafka header → consumer. This cross-Kafka propagation detail impresses.
  • OpenFeign: declarative REST clients with a custom ErrorDecoder mapping partner 4xx/5xx to domain exceptions — mention as an option alongside WebClient/RestClient.
Trap: "Why circuit breaker at all if the LB retries?"

Retry without a breaker amplifies an overloaded dependency (retry storm); the breaker sheds load and fails fast. Use both, with backoff.

Trap: "Config server is down at startup — what happens?"

Services fail fast (fail-fast=true) unless config is cached / retried — mention caching + retry as the production answer.

Trap: "Security group vs NACL?"

SG = stateful, instance/ENI level; NACL = stateless, subnet level (needs allow rules for return traffic).

Trap: "RDS multi-AZ vs read replica?"

Multi-AZ = availability (synchronous standby, automatic failover); read replica = scalability for reads (async, promotable).

Trap: "App is slow — how do you find the bottleneck on AWS?"

Follow the chain, don't guess: CloudWatch infra metrics → Grafana app metrics/traces → ELK logs by traceId → narrow to DB / GC / dependency. Shows a method.

Frontend 1 Angular data binding

    • Event binding (click)="save()" — component ← DOM.

  • Component communication: parent→child @Input(), child→parent @Output() + EventEmitter.
  • Change detection: default checks everything; we use OnPush + immutable updates + async pipe so Angular checks only on input reference change / event / observable emission — ties into the ~40% load/interaction story.
  • If asked "what's new": on Angular 17+, signals (signal(), computed()) = value + dependency tracking, fine-grained reactivity without zone-based tree walks.

Frontend 2 Observables / RxJS

  • What: a lazy push-based stream of values over time; subscriber gets next / error / complete. HttpClient returns a cold observable — nothing happens until subscribe.
  • Unsubscribe discipline (always asked): async pipe (auto-unsubscribes, works with OnPush) or takeUntilDestroyed(this.destroyRef); leaking subscriptions = memory leaks + stale API calls.
  • Operators with real portal examples:
    • debounceTime(300) + distinctUntilChanged() — transaction search box.
    • switchMap — typeahead: cancels the stale request on new input. The trio: switchMap (cancel stale — searches) / concatMap (order matters — sequential saves) / exhaustMap (ignore while in-flight — login submits).
    • forkJoin — parallel dashboard API loads, render when all done; combineLatest — live filter + data streams.
    • catchError → throwError(() => new ApiError(...)) or EMPTY + user toast; retry APIs with retry({ count: 2, delay: 500 }).
    • shareReplay(1) — cache reference data (currencies, branches): one HTTP call shared by many components.
  • State: BehaviorSubject for local service state; NgRx for cross-module state — component dispatches action → reducer produces new state → selectors → async pipe; effects isolate side effects. One-liner: "state as immutable single source of truth."

Frontend 3 Interceptors

  • What: middleware on every HTTP call in/out (a chain, order matters — we register auth → trace-id → error).
  • Angular 15+ style: functional interceptor — authInterceptor: HttpInterceptorFn = (req, next) => ... (say you use the modern functional form; matches your Angular 15+ story).
  • Auth interceptor: req.clone({ setHeaders: { Authorization: 'Bearer ' + token } }).
  • The 401 refresh flow — know it step by step:
    1. Call fails with 401 → catchError → skip if the request is the refresh call (marker header/context).
    2. Call authService.refresh() and share the in-flight refresh observable — 10 parallel 401s trigger ONE refresh; the rest queue on it.
    3. On success, switchMap → retry the original request with the new token.
    4. Refresh also fails → logout + redirect.
  • Other uses we have: inject X-Trace-Id header (correlates with backend ELK logs — connects to your BE story), normalize HTTP errors into the app error model, dev logging.

Frontend 4 Authorization (Authorized) in Angular

  • Guards — functional style (v15+): canActivate: [authGuard, roleGuard]; guard returns boolean | UrlTree (UrlTree redirects to /login or /403).
    • authGuard: token exists / not expired; async validation returns Observable<boolean>.
    • roleGuard: reads required roles from route data (data: { roles: ['ADMIN'] }), compares with decoded JWT claims (jwt-decode).
  • Guard types: CanActivate (page), CanActivateChild (subtree), CanMatch (v15+, replaces CanLoad — blocks even downloading the lazy chunk), CanDeactivate (unsaved form warning).
  • UI-level: structural directive *appHasRole="'ADMIN'" to hide buttons; role-based menu config.
The line that scores points: "Frontend authorization is UX only — every route and action is re-authorized server-side: JWT verified at the Spring Cloud Gateway, method-level with @PreAuthorize in the services, and data-layer checks. Bypassing the UI still gets a 403." (Mirrors the RBAC bullet in your CV.)

Rehearse 90s STAR story to have ready

Situation: peak-season load → a consumer group rebalance caused event redelivery → customers received duplicate SMS/email notifications.

Task: guarantee single delivery without losing the at-least-once safety net.

Action: event_id dedupe table + Redis TTL cache checked before processing; manual offset commit only after successful processing; cooperative-sticky assignor to reduce rebalances; DLT + alerting for anything still failing.

Result: zero duplicate sends after rollout; consumer-lag alarm tuned on Grafana; the same dedupe pattern got reused by two other teams.
