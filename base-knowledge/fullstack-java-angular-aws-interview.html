Backend 0 Java core — bản dễ đọc (hỏi gì, trả lời nấy)

Where in your story: Java 8→21 across all projects. The client tests Java strength, so expect these. Cách dùng: đọc câu hỏi → thử trả lời miệng → mở ra so sánh. Trả lời thật 1–3 câu đơn giản rồi dừng — chỉ đào sâu khi họ hỏi tiếp.

Collections

"HashMap hoạt động bên trong thế nào?"

"Think of it as an array of buckets. When you put(key, value), Java takes the key's hashCode() to choose a bucket and stores the entry there. get(key) computes the same hash and goes straight to that bucket — that's why it's fast, O(1) on average. If two keys land in the same bucket, they form a small list inside it — and since Java 8, a long list becomes a balanced tree, so even collisions stay fast."

Tiếng Việt: như tủ nhiều ngăn đánh số — hashCode quyết định ngăn nào. Lấy đồ: tính số rồi đi thẳng tới ngăn. Hai key trùng ngăn thì thành danh sách, dài quá (8+ phần tử) thì chuyển thành cây để vẫn nhanh.

"Vì sao phải override cả equals lẫn hashCode?"

"Because HashMap finds the bucket with hashCode, then compares keys with equals. If two 'equal' objects have different hashCodes, they end up in different buckets — get() returns null even though you just put it in. Rule: equal objects must have equal hashCodes. Records and the IDE generate both correctly — the classic bug is overriding equals but not hashCode."

Tiếng Việt: hashCode tìm ngăn, equals xác nhận đúng key trong ngăn. Override equals mà quên hashCode → 2 object "bằng nhau" nằm 2 ngăn khác → tìm không ra.

"HashMap có thread-safe không? Không thì dùng gì?"

"No. Two threads writing at the same time can corrupt it, and modifying while iterating throws ConcurrentModificationException. For multi-threaded access we use ConcurrentHashMap — it locks per bucket, so threads rarely block each other, and it doesn't allow null keys or values."

Tiếng Việt: HashMap dùng chung nhiều thread → hỏng dữ liệu / lỗi ConcurrentModificationException (vừa duyệt vừa xóa). Chuyển sang ConcurrentHashMap — khóa theo từng ngăn nên ít chặn nhau.

"Vì sao String immutable?"

"Three reasons: security — once checked, a String value like a filename or URL can't be swapped underneath; thread-safety for free; and performance — the hash is computed once and cached, and string literals share one pool in memory."

Tiếng Việt: An toàn (kiểm tra xong không ai đổi giá trị được), thread-safe miễn phí, hash cache 1 lần + dùng chung string pool.

Multithreading

"volatile là gì? Có đủ để đếm số an toàn không?"

"volatile means every thread sees the latest value immediately — no stale local copies. Good for a simple flag like 'stop'. But it does NOT make count++ safe, because count++ is three steps: read, add, write — two threads can interleave. For counters I use AtomicInteger — lock-free, based on compare-and-swap."

Tiếng Việt: volatile = thread nào đọc cũng thấy giá trị mới nhất ngay (hợp cho biến flag). Nhưng count++ gồm 3 bước read-add-write nên vẫn sai → dùng AtomicInteger.

"synchronized vs ReentrantLock?"

"Both let only one thread in at a time. synchronized is simpler — the lock opens automatically, even on exception. ReentrantLock is for advanced cases — take the lock with a timeout, interruptible waiting, fair ordering. I default to synchronized, or better, the ready-made classes in java.util.concurrent that avoid manual locking altogether."

Tiếng Việt: Cả hai đều cho 1 thread vào vùng critical tại một thời điểm. synchronized đơn giản, tự nhả khóa kể cả khi exception. ReentrantLock dùng cho ca đặc biệt: chờ có timeout, interrupt được.

"Sao phải dùng thread pool? Cẩn thận gì?"

"Creating threads is expensive, so pools reuse them. We use fixed-size pools with a bounded queue and named threads. The dangerous one is newCachedThreadPool — it creates unlimited threads under load and can crash the app. And when the queue is full you need a rejection policy — we log and alert; sometimes CallerRunsPolicy to slow the producer down."

Tiếng Việt: Tạo thread tốn kém → pool tái sử dụng. Tránh newCachedThreadPool (tạo thread vô hạn khi tải cao). Queue phải có giới hạn + quyết định rõ hành vi khi đầy.

"CompletableFuture dùng khi nào?"

"When I need to call two partner APIs at the same time and combine the results — supplyAsync with our own executor, then thenCombine or allOf, and handle errors with exceptionally. One detail that matters: pass your own thread pool. The default shared pool is small and meant for CPU work, not threads waiting on network."

Tiếng Việt: Gọi 2 API song song rồi gộp kết quả. Nhớ truyền executor riêng — pool mặc định nhỏ, không dành cho việc chờ mạng.

"Virtual threads (Java 21) là gì?"

"Very cheap threads made for code that waits on the network. You can run thousands of them blocked on IO without memory problems. We're piloting them for partner calls. Two rules: don't pool them — create per task; and limit concurrency with a semaphore, not a pool size."

Tiếng Việt: Thread "rẻ" cho tác vụ chờ mạng — mở hàng nghìn cái thoải mái. Đừng pool chúng; muốn giới hạn thì dùng semaphore.

JVM & GC

"Bộ nhớ JVM có những gì?"

"Day to day two areas matter: the heap, where all objects live and GC cleans up; and one stack per thread, holding local variables. Plus metaspace for class metadata. So a memory leak in Java is objects still referenced but never used again — usually stuck in a cache or a listener list."

Tiếng Việt: Heap chứa object (GC dọn), mỗi thread có stack riêng chứa biến cục bộ, metaspace chứa thông tin class. Memory leak = object còn được tham chiếu nhưng không ai dùng nữa — thường kẹt trong cache hoặc danh sách listener.

"GC hoạt động thế nào? G1, ZGC khác gì?"

"GC frees objects nothing references anymore. The default is G1 — it splits the heap into regions and cleans them step by step, keeping pauses short; ZGC is for apps needing sub-millisecond pauses on big heaps. And when we get memory alerts, the routine is fixed: thread dump first to see what's stuck, then heap dump, then look at the biggest objects — usually a query loading too much data or an unbounded cache."

Tiếng Việt: GC tự dọn object không còn tham chiếu. Mặc định G1 (chia heap thành vùng, dọn từng phần, pause ngắn); ZGC cho hệ cần pause cực ngắn. Sự cố memory: thread dump → heap dump → xem object nào chiếm nhiều nhất.

"Stream vs vòng lặp thường?"

"Streams for declarative transforms — filter, map, collect — especially two-step chains; classic loops when the logic is simple or performance-critical. Readability decides. And I'm careful with parallelStream — it shares one small common pool, so I don't use it inside request threads."

Tiếng Việt: Stream hợp cho phép biến đổi dữ liệu (filter/map/collect); vòng lặp cho logic đơn giản. Ưu tiên cái nào dễ đọc. Cẩn thận parallelStream trong web request.

Trap: "final field là thread-safe rồi chứ?"

Gần đúng, đừng trả lời "đúng" — final List<String> list thì con trỏ không đổi nhưng vẫn add() được → vẫn phải đồng bộ. Nói: "final makes the reference immutable and gives safe publication, but if it points to a mutable object, the object itself still needs synchronization."

Leaked Java version upgrades — "có hay update? Quy trình? Chú ý gì?"

Leaked from R1: three Java-upgrade questions in a row. Your CV says Java 8–21 and the platform runs 17/21 — the story: started on 8, stepped 8→11→17, now 17 everywhere with 21 rolling out for partner-call services (virtual threads).

45-second answer to "em có hay update Java version không?"

"Yes — we treat JDK upgrades as small migration projects, and we follow LTS releases only: 8 → 11 → 17, and now 17 with 21 being adopted for new services. Why: security patches, GC and startup improvements, better container awareness, and framework pressure — Spring Boot 3 requires Java 17. The rule I follow: never jump JDK and framework majors in the same release — upgrade dependencies first, then the JDK, one service at a time."

The process (answer to "quy trình update thế nào?")

  1. Inventory & compatibility matrix first: Spring Boot / Hibernate / build plugins / Docker base image / CI agents / Sonar / Lombok-MapStruct — everything that touches bytecode.
  2. Build pipeline first: CI builds on the new JDK (maven.compiler.release=17), Docker base image bump (eclipse-temurin:17) — nobody's laptop is special.
  3. Compile-fix loop: removed APIs, javax → jakarta (Boot 3), reflection into JDK internals → upgrade the offending library, or bridge with --add-opens temporarily.
  4. Automated safety net: full unit + Testcontainers integration + contract tests; Sonar gate; dependency scans — before any human testing.
  5. Performance validation on staging: GC logs before/after (defaults change between versions), startup time, load-test comparison; JVM flag audit — removed flags (e.g. old CMS options) stop the JVM from starting at all, so you want that discovered in staging, not prod.
  6. Canary rollout: lowest-risk service first, one service per release train, rollback = redeploy the previous image tag.

Backend 0.5 Hibernate / JPA (banking = data layer questions)

Where in your story: the whole data layer of the orchestration platform — Spring Data JPA, complex JPQL, stored procedures, Flyway, indexing (straight from the CV, incl. the 40% query win).

Core answers

  • Entity lifecycle: transient → managed (persist/find) → detached (tx ends) → removed. Dirty checking: managed entities are diffed at flush — you don't call update(); that's the #1 JPA misconception to get right.
  • save vs persist vs merge: Spring Data save() calls persist for new entities (null id/version) else merge. merge copies state into a new managed instance — the original stays detached; keep using the return value.
  • N+1 (they WILL ask): 1 query for parents + 1 per parent for a lazy association. Detect with SQL logging / hibernate.generate_statistics. Fix ladder: JOIN FETCH in JPQL → @EntityGraph(attributePaths = …) → @BatchSize / hibernate.default_batch_fetch_size=50 (in-batch loading) → DTO projections for read-only screens (no entity management at all).
  • Pagination + collection fetch trap: JOIN FETCH a collection with Pageable → Hibernate warns HHH000104 and paginates in memory. Fix: page a parent-id query first, then fetch children WHERE parent_id IN (…).
  • LazyInitializationException: proxy accessed after the session closed. Right fix: fetch what the view needs inside the service boundary and map to DTOs. We disable open-in-view (spring.jpa.open-in-view=false) so the problem surfaces in dev, not as a prod surprise.
  • getID strategies: IDENTITY forces a per-row round-trip and disables JDBC insert batching; use SEQUENCE + allocationSize=50 with hibernate.jdbc.batch_size=50, order_inserts=true — this is exactly how we made batch writes fast.
  • Locking: optimistic @Version (Spring translates to ObjectOptimisticLockingFailureException; retry the business op) — default everywhere; pessimistic LockModeType.PESSIMISTIC_WRITE (SELECT … FOR UPDATE) only on hot contention like balance-style rows.
  • First-level cache = the persistence context, per transaction, free; second-level cache — we skip it and cache projections in Redis instead (invalidation is business-driven and explicit).
  • Migrations: Flyway versioned V123__desc.sql + repeatable R__views.sql, expand/contract pattern for zero-downtime schema changes (add column → backfill → switch reads → drop).
  • The 40% story, decomposed: slow-query log + EXPLAIN → missing composite indexes (order by selectivity) → rewritten N+1 to joins/projections → Redis cache-aside for hot reference data → correct fetch strategies.
Trap: "getReference vs findById?"

getReference returns a lazy proxy with no SQL — perfect to set an FK (order.setUser(userRef)); findById actually loads the row. Also mention: accessing a proxy's state after session close → LazyInitializationException.

Trap: "Why did a flushed change appear without any save() call?"

Dirty checking: any managed entity changed inside a transaction is written at flush. Calling save on managed entities is mostly a no-op habit from other ORMs.

Trap: "Batch insert of 100k rows is slow — what do you check?"

IDENTITY id strategy (kills batching) → switch to SEQUENCE; enable jdbc.batch_size + order_inserts; clear the persistence context every N entities (memory + dirty-check cost); consider plain JDBC/JdbcTemplate for pure loads.

Backend 1 Apache Kafka

Where in your story: event backbone of the orchestration platform — payment orchestration events, notification dispatch (email/SMS), audit trail. Multiple consumer services read the same events.

Core answers

  • Why Kafka over RabbitMQ/SQS: pull-based append-only log with retention → consumers can replay history (audit/recovery/new services), much higher throughput, multiple independent consumer groups on the same topic. Queue systems delete on ack; the log is the difference.
  • Architecture: brokers; topics split into partitions (unit of parallelism & ordering); each partition has a leader and follower replicas; ISR = in-sync replicas; leaders fail over to an ISR member; KRaft replaced ZooKeeper for metadata (Kafka 4.x is KRaft-only). MSK abstracts all of this — we tune partitions/retention, not broker ops.
  • Delivery semantics: default at-least-once. We make processing effectively-once: (1) idempotent producer (enable.idempotence=true, acks=all, min.insync.replicas=2) — broker dedupes by producer-id + sequence; (2) idempotent consumers — dedupe by event_id in Redis/DB before side effects.
  • Ordering: guaranteed only within a partition. We key by transactionId/accountId (default partitioner = murmur2(key) % partitions) so each entity's events stay ordered; global order isn't needed — say that explicitly.
  • Producer tuning: linger.ms + batch.size (throughput vs latency), compression (lz4/zstd), delivery.timeout.ms bounds the total send attempt window.
  • Consumer mechanics: heartbeats keep group membership (session.timeout.ms); polls prove liveness (max.poll.interval.ms) — a slow batch that stops polling gets evicted → rebalance storm. Cooperative-sticky assignor makes rebalances incremental instead of stop-the-world; static membership (group.instance.id) survives restarts without rebalance.
  • Offset management: commit = checkpoint; we ack after successful processing (Spring AckMode.RECORD/MANUAL). Poison pill → DLT or seek-past-and-record — never block the partition.
  • Error handling (they WILL ask): Spring Kafka @RetryableTopic — non-blocking retries with backoff on retry topics (-retry-0/1/…) → DLT with @DltHandler + Grafana alerting and an ops dashboard for triage/replay. Know the trade-off: retry topics break per-key ordering — if order matters for that event, retry inline (blocking) or use per-key retry lanes.
  • Schema governance: Schema Registry + Avro; compatibility modes — BACKWARD (new consumers read old data), FORWARD, FULL; producers can't register breaking schemas. Alternatives: JSON Schema / Protobuf.
  • Lag monitoring: lag = log-end-offset − committed offset; Kafka exporter → Grafana alert before SLA hurt. Remedies: more partitions + listener concurrency, batch listeners, and backpressure via container pause()/resume().
  • DR: MirrorMaker 2 (or MSK replication) to a second region; consumers offset-translate on failover.
Senior kill-shot — Transactional Outbox pattern.
Problem: dual-write — commit DB tx then publish to Kafka and the publish fails (or vice versa) → inconsistency.
Solution: write the event to an outbox table inside the same DB transaction as the business change; a relay (poller, or Debezium CDC on MSK Connect) publishes it to Kafka. Kafka publish is never inside the DB transaction. Deploy this answer whenever they ask about DB↔Kafka consistency, sagas, or "how do you avoid distributed transactions".
Trap: "Is Kafka exactly-once?"

The transactional producer (transactional.id) gives EOS for Kafka→Kafka consume-transform-produce (consumers set isolation.level=read_committed). For side-effectful consumers (send SMS, write external API) you still dedupe: at-least-once delivery + idempotent processing. "Effectively-once end-to-end" is the honest phrasing.

Trap: "Consumer lag spikes at peak — what do you do?"

First: is it throughput or a stuck consumer? Check thread/GC health, then scale: partitions + concurrency (≤ partitions per instance), batch listeners, fetch.min.bytes. Longer term: alert on lag-rate, not absolute lag.

Trap: "How many partitions should a topic have?"

Target max throughput × headroom, but bounded: partitions multiply open files, leader elections, and end-to-end latency (more replication), and you can add partitions later but never reorder — key-to-partition mapping breaks. We start with growth headroom (e.g., 12) and size consumers to match.

Trap: "min.insync.replicas=2 with acks=all — why not 3?"

With RF=3, min ISR=2 tolerates one broker down while still blocking writes only when two are down. min ISR=3 means any single broker failure stops all writes — availability gone. It's the durability/availability dial.

Backend 2 Elasticsearch

Where in your story: the CV's exact claim — "Grafana monitoring dashboards with centralized ElasticSearch logging". Transaction search = stretch claim (not on the CV) — lead with logging, offer search only if you can defend the search_after story below.

Core answers

  • Why not SQL LIKE '%x%': leading wildcard = full table scan, no index. ES builds an inverted index (token → posting list of docs) at index time → fast full-text + filters. Shard = a Lucene index; segments are immutable (that's why updates = mark-delete + append).
  • Our pipeline: services log structured JSON with trace_id → Filebeat → Logstash (parse/enrich) → ES → Grafana/Kibana. Trace ID correlates one request across gateway → services → Kafka consumers.
  • Text vs keyword (mapping): text = analyzed full-text (match queries, relevance); keyword = exact filter/agg/sort. Explicit mappings in prod — dynamic mapping guessing wrong ruins aggregations. Zero-downtime mapping change: reindex behind an alias, swap alias when done.
  • Analysis chain: character filters → tokenizer → token filters (lowercase, stemmer). For autocomplete we use edge n-grams / search_as_you_type; normalizer (e.g. lowercase) for keyword fields.
  • Query DSL: bool with must (scored) / filter (non-scoring, cacheable — put status/date ranges there) / should / must_not. match vs term (analyzed vs exact) vs match_phrase (ordered proximity).

Trap: "Is ES a primary datastore?"

No: no joins/ACID across documents, near-real-time, eventual consistency. PostgreSQL stays the source of truth; ES is a search/projection rebuilt from the source (external versioning keeps them in sync).

Trap: "Filter vs query context?"

Filter context is non-scoring and cacheable — put exact conditions (status, date range) in filter; only relevance terms in must. Free performance, one-word answer.

Trap: "Cluster is red / slow — first moves?"

Red = unassigned primaries (disk watermark, node down) — check allocation explain. Slow: hot threads API, are queries fetching huge size? too many shards per GB heap (~aim ≤ 20/GB)? heavy aggregations on high-cardinality keyword fields?

Backend 3 Spring Batch

Where in your story: CV words — "report generation, data synchronization, backup operations, and automated compliance checks". Your concrete story: a nightly data-sync job (reconciliation-style checks vs partner data) + monthly compliance reports — millions of records.

Core answers

  • Chunk-oriented model: read → process → write per chunk; each chunk = its own transaction (commit-interval). ItemReader → ItemProcessor (return null = filter, not skip) → ItemWriter. Tasklet = single-task step (cleanup, API call).
  • The metadata model (know cold): JobInstance = job name + identifying parameters; each run = JobExecution → StepExecutions, all persisted by the JobRepository. Consequences: restartability (failed execution resumes from the step's ExecutionContext checkpoint — e.g. read.count), and run-idempotency (same params + COMPLETED → JobInstanceAlreadyCompleteException); daily runs need a run.id incrementer parameter.
  • Fault tolerance: skip (SkipPolicy + skip-limit; bad rows logged by SkipListener to a dead-letter table for ops) and retry (per-item, for transient errors like deadlock or partner 503s):
    faultTolerant().skip(FlatFileParseException.class).skipLimit(100).retry(DeadlockLoserDataAccessException.class).retryLimit(3)
  • How skip actually works (senior detail): a failing item rolls back the whole chunk, then Spring re-scans the chunk item-by-item and skips only the offender — so failures cost a re-read, and skip-limit protects against pathological files.
  • Scaling ladder: single-threaded → multi-threaded step (readers/processors must be thread-safe; stateless processors) → parallel steps (flows) → partitioning (manager splits by date-range/range into worker step executions — our default for reconciliation) → remote chunking/partitioning over Kafka for very big loads (workers get chunks via topics; watch backpressure).
  • Reader restartability: paging readers (JpaPagingItemReader) checkpoint cleanly; cursor readers (JdbcCursorItemReader) hold a DB cursor — for them use the process-indicator pattern (mark rows processed) or restartable queries.
  • Tuning: align chunk size with reader page size (we use 500–1000), never load all in memory, IDENTITY→SEQUENCE + JDBC batching for inserts, clear persistence context every N items; listeners push duration/skip/read-count metrics to Grafana via Micrometer.
  • Scheduling & single-runner: Quartz/@Scheduled + a distributed lock (ShedLock/DB lock) so exactly one node runs the job in a multi-pod deployment; graceful stop via JobOperator.stop() mid-chunk so restart picks up from the checkpoint.
  • Flow control: exit status → conditional transitions (.on(FAILED).to(errorStep)), decide with JobExecutionDecider; stopAndRestart(step) for controlled pauses.
  • Spring Batch 5 (Boot 3): builders take the JobRepository explicitly (new JobBuilder("job", jobRepository) — old JobBuilderFactory removed), transaction manager passed to the chunk step; know this so version talk doesn't trip you.
Trap: "Chunk transaction fails at item 990 — what happens?"

Whole chunk rolls back. With skip configured, Spring re-reads the chunk and processes item-by-item, skipping only the offender; the job continues with the next chunk. Without skip/retry, the step fails and the job restarts later from the checkpoint.

Trap: "Same job must run twice a day — what breaks?"

Identifying params identical → treated as the same JobInstance. Add a distinguishing parameter (timestamp or run.id via JobParametersIncrementer).

Trap: "Restart replays writes — duplicates?"

Writers must be idempotent/restart-aware: chunk-level the repository tracks committed chunks, but for external side effects use idempotent writes (upsert by natural key) — same principle as the Kafka consumer dedupe.

Backend 4 @Transactional in Spring

Where in your story: anywhere money moves — orchestration sagas, payment records, audit logs. Leaked: "Transactional hoạt động thế nào" was asked word-for-word — open with this, then let them drill.
60-second spoken answer:
"It's implemented with Spring AOP: when the container creates the bean it wraps it in a proxy. When a call enters a @Transactional method through the proxy, the TransactionInterceptor begins a transaction on the connection — joining an existing one under REQUIRED — commits on normal return, and rolls back on uncaught RuntimeException or Error. Checked exceptions do not roll back by default, so on money paths we set rollbackFor explicitly. Two gotchas we guard against in code review: self-invocation bypasses the proxy so no transaction starts, and a failed inner REQUIRED marks the tx rollback-only, so an outer catch explodes with UnexpectedRollbackException at commit. And we keep transactions short — no HTTP or Kafka inside — side effects go through an outbox written in the same transaction."

Core answers

  • How it works: Spring AOP wraps the bean in a proxy (JDK dynamic proxy on interfaces, CGLIB subclass otherwise); TransactionInterceptor begins/commits/rolls back around external, public method calls. Only calls that enter through the proxy are transactional.
  • Rollback rules (classic): default rolls back on RuntimeException and Error only — checked exceptions do NOT roll back unless rollbackFor = Exception.class. We set it explicitly on money-path methods where checked partner exceptions exist.
  • Propagation:
    • REQUIRED (default) — join existing or create new.
    • REQUIRES_NEW — suspends outer tx, fully independent commit/rollback. Our use: the audit log of a failed attempt must persist even when the main payment tx rolls back.
    • NESTED — savepoint inside the same physical tx (JDBC; awkward with JPA — most teams model it as REQUIRES_NEW).
    • MANDATORY (fails without tx), NEVER (fails with tx), NOT_SUPPORTED (suspends), SUPPORTS — know the names.
  • Isolation & anomalies: PostgreSQL default READ_COMMITTED; MySQL InnoDB REPEATABLE_READ (MVCC + gap locks). Ladder: dirty read → non-repeatable read → phantom read. Beyond the ladder: lost update (two read-modify-writes) and write skew (two constraints each valid alone). In practice we don't raise isolation — we use optimistic @Version, pessimistic SELECT … FOR UPDATE only on hot rows (links to the JPA section).
  • The three classic bugs:
    1. Self-invocation: this.method2() inside the same bean bypasses the proxy → no transaction. Fix: move it to another bean (or self-injection / TransactionTemplate).
    2. Private/final/static methods — proxy can't intercept/override.
    3. UnexpectedRollbackException: inner REQUIRED method throws, someone catches it upstream, outer tries to commit → the tx was already marked rollback-only → commit explodes. Fixes: don't swallow, noRollbackFor, or make the inner REQUIRES_NEW. This trap is a senior-level filter — know it cold.
  • Keep transactions short: never Kafka/HTTP/SMTP inside a DB tx → pool exhaustion under load + dual-write problem → outbox pattern. Best-effort alternative: TransactionSynchronization afterCommit callback — but outbox is the durable answer.
  • readOnly = true: Hibernate skips dirty-checking snapshots (FlushMode.MANUAL) + driver hint; can also route to a read replica with a routing DataSource.
  • Pool math (nice senior touch): HikariCP isn't "bigger is better" — formula ≈ cores × 2 + spindles; more connections = more DB contention. Symptom of starvation: Connection is not available, request timed out after 30000ms → find the tx holding connections (long tx / external call inside tx).
  • Transactions don't cross threads: context lives in a ThreadLocal — @Async inside a tx loses it; same reason @Transactional doesn't propagate into CompletableFuture tasks.
  • Why no XA/2PC: it exists, but blocking + coordinator fragility; we choose sagas + outbox + idempotency + reconciliation batch — say the whole sentence, it ties three sections together.
Trap: "Outer REQUIRED + inner REQUIRES_NEW; inner rolls back — what does outer see?"

Inner is independent: it rolled back, its locks released. Outer continues and can still commit — unless the inner exception propagates and trips outer's rollback rules. And REQUIRES_NEW holds a second connection — nested deeply under load = pool deadlock risk.

Trap: "How do you test transactions?"

@DataJpaTest is transactional-rollback by default — REQUIRES_NEW and afterCommit are invisible inside it. Test real commits/failures with Testcontainers Postgres and @Commit/manual cleanup.

Trap: "@Transactional on a @KafkaListener method — worth it?"

Yes — the listener container can run each record/loop in a Spring-managed tx so DB writes + offset commit align. Combine with outbox reads for the Kafka side. AckMode choice (BATCH/RECORD/MANUAL) decides when offsets commit relative to the tx.

OnPush narrows checks to: input-reference change, events from the component, markForCheck(), signal reads, async pipe emission. Immutable updates are what make OnPush actually fire — the trio: OnPush + immutability + async pipe = the ~40% load story.
  • trackBy in *ngFor / track in @for: identity-stable keys let Angular reuse DOM nodes instead of re-creating rows — list rerenders are the classic jank source in transaction tables.
  • Pipes: pure by default (recomputed only when input reference changes — free); async pipe is intentionally impure (subscribes/unsubscribes on every check) — it's the bridge between RxJS and the template.
  • Modern Angular you can claim: standalone components (no NgModules), signal inputs input() / two-way model(), computed()/effect(), and the @if/@for control flow (17+) — we generate typed API clients from OpenAPI so components bind to DTO types end-to-end.
  • Structural directives: the * is sugar for wrapping the template in <ng-template>; custom ones manipulate TemplateRef + ViewContainerRef (that's how our *appHasRole works).
Trap: "OnPush component didn't update — why?"

Someone mutated the input object in place (same reference = no check) or updated outside Angular's knowledge. Fix: new reference/immutable update, markForCheck(), or move the state into a signal the template reads.

Trap: "Signals vs Observables — which do you use?"

Signals for synchronous state the template reads (fine-grained, no tree walk); Observables for async streams (HTTP, websockets) bridged with toSignal() from rxjs-interop. Pragmatic mix, not a religion.

Frontend 2 Observables / RxJS

  • What: a lazy push-based stream of values over time; subscriber gets next/error/complete. HttpClient returns a cold observable — nothing happens until subscribe; each subscriber re-triggers the request.
  • Unsubscribe discipline (always asked): async pipe (auto-unsubscribes, plays perfectly with OnPush) or takeUntilDestroyed(this.destroyRef); leaking subscriptions = memory leaks + stale API calls racing fresh ones.
  • Higher-order mapping — the decision table (memorize):
    OperatorBehaviorPortal example
    switchMapcancel stale inner streamtypeahead / transaction search
    concatMapqueue, order preservedsequential saves / file uploads in order
    mergeMapall in parallel, order-freefan-out notifications
    exhaustMapignore new while in-flightlogin/submit button
  • Combining — second table they love: forkJoin = Promise.all (last value of each, completes when all do) for dashboard loads; combineLatest = latest of each after each has emitted — live filter + data; zip = pairwise by index; withLatestFrom = snapshot of another stream at emit time (action + current form state).
  • Error strategy subtlety: catchError at the top level ends the stream (subscription dies); placed inside a switchMap it protects the outer stream and lets it continue. Retries: retry({ count: 2, delay: 500 }) (retryWhen is legacy).
  • Sharing: shareReplay({ bufferSize: 1, refCount: true }) — one HTTP call, many subscribers (reference data: currencies, branches).
  • Subjects family: BehaviorSubject (replays current value — local service state, "current user"), ReplaySubject(n), AsyncSubject (last on complete). One caution: an error on a Subject terminates all its subscribers — guard the source.
  • Realtime (CV bullet): Spring WebSocket/STOMP consumed as an RxJS subject — live transaction updates; reconnection with exponential backoff + jitter.
  • State: BehaviorSubject for local service state; NgRx for cross-module state — dispatch action → reducer → memoized selectors → async pipe; effects isolate side effects (ofType + concatMap); entity adapter for collections. One-liner: "state as immutable single source of truth."
  • Promises interop: firstValueFrom(obs) when async/await is genuinely clearer — but in templates, the async pipe wins.
Trap: "Search sends a request per keystroke — fix it"

valueChanges.pipe(debounceTime(300), distinctUntilChanged(), switchMap(search)) — and handle errors inside the switchMap so one failed search doesn't kill the listener.

Trap: "Cold vs hot — and how do you make a cold one hot?"

Cold: one fresh execution per subscriber (HTTP). Hot: one execution shared (Subjects, fromEvent). Bridge: share()/shareReplay() or connect() — this is exactly the refresh-token queue pattern in the interceptor.

Frontend 3 Interceptors

  • What: middleware on every HTTP call in/out — a chain where order matters: provideHttpClient(withInterceptors([authInterceptor, traceInterceptor, errorInterceptor, loadingInterceptor])).
  • Angular 15+ style: functional interceptor — authInterceptor: HttpInterceptorFn = (req, next) => next(req.clone({ setHeaders: { Authorization: 'Bearer ' + token } })). Skip-auth for public endpoints via HttpContextToken + req.context.set(SKIP_AUTH, true) — a detail that signals real usage.
  • The 401 refresh flow — know it step by step:
    1. Call fails with 401 → catchError → skip if the request is the refresh call (marker/context) to avoid loops.
    2. Call authService.refresh() and share the in-flight refresh observable (share() or a BehaviorSubject gate) — 10 parallel 401s trigger ONE refresh; the rest queue on it.
    3. On success, switchMap → retry the original request with the new token.
    4. Refresh also fails → logout + redirect to login (clear state; optional BroadcastChannel to sync logout across tabs).
  • Other uses we have: inject X-Trace-Id header (correlates with backend ES logs — connects to the BE story), normalize HTTP errors into the app error model (backend envelope code → typed domain errors), retry-with-backoff for idempotent GETs, and a loading counter via finalize(() => count--) driving the global spinner.
  • Uploads/downloads: reportProgress: true + filter HttpEventType.UploadProgress for progress bars on report exports.
  • Scope note: interceptors only see HttpClient — router navigation errors are handled by guards/router events, not interceptors.

Be able to WRITE it (recruiter leak: FE focus = HttpInterceptor)

export const SKIP_AUTH = new HttpContextToken<boolean>(() => false);

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);
  const authReq = auth.token && !req.context.get(SKIP_AUTH)
    ? req.clone({ setHeaders: { Authorization: `Bearer ${auth.token}` } })
    : req;
  return next(authReq).pipe(
    catchError((err: HttpErrorResponse) =>
      err.status === 401 && !req.context.get(SKIP_AUTH)
        ? retryWithRefresh(authReq, next, auth)
        : throwError(() => normalize(err)))
  );
};

// ONE shared in-flight refresh — N parallel 401s trigger a single refresh call
let refresh$: Observable<unknown> | null = null;
function retryWithRefresh(req: HttpRequest<unknown>, next: HttpHandlerFn, auth: AuthService) {
  if (!refresh$) {
    refresh$ = auth.refresh().pipe(
      tap(() => (refresh$ = null)),   // next expiry starts a fresh refresh
      share()
    );
  }
  return refresh$.pipe(
    switchMap(() => next(req.clone({ setHeaders: { Authorization: `Bearer ${auth.token}` } }))),
    catchError(() => {
      auth.logout();                   // refresh failed → session over
      return throwError(() => new Error('session expired'));
    })
  );
}

// registration: provideHttpClient(withInterceptors([authInterceptor, ...]))
Trap: "Why share() the refresh call — what breaks without it?"

Without sharing, N failed requests each trigger a refresh; the first refresh invalidates the old token so the others' refresh calls fail → mass logout. Sharing = single refresh + everyone retries on the new token.

Trap: "CORS error — do you fix it in the interceptor?"

No — CORS is enforced by the browser against server response headers. Fix at the edge: gateway/backend CORS config. Interceptors can't bypass preflight.

Frontend 4 Authorization (Authorized) in Angular

  • Guards — functional style (v15+): canActivate: [authGuard, roleGuard]; guard returns boolean | UrlTree | Observable<boolean> (UrlTree redirects to /login or /403).
    • authGuard: token exists / not expired (async validation via Observable).
    • roleGuard: reads required roles from route data (data: { roles: ['ADMIN'] }), compares with decoded JWT claims (jwt-decode).
  • Guard types: CanActivate (page), CanActivateChild (subtree), CanMatch (v15+; supersedes CanLoad — blocks even downloading the lazy chunk: unauthorized users never receive admin-bundle code), CanDeactivate (unsaved-form warning, our transaction-config screens).
  • UI-level: structural directive *appHasRole="'ADMIN'" (TemplateRef + ViewContainerRef) hides buttons; role-based menu config — same RBAC permissions the backend enforces (mirrored from the CV bullet).
  • Modern SPA auth (drop these terms): OAuth 2.0 Authorization Code + PKCE — implicit flow is deprecated; access token kept in memory, refresh token in an httpOnly secure cookie (XSS can't read it) — explain why not localStorage. JWT checked for exp/claims locally only as UX.
  • SAML (it's on your CV — one-liner ready): "JWT-based auth and OAuth 2.0 flows for our APIs, plus SAML SSO for enterprise client logins" — SAML = XML assertion from an identity provider (Okta/ADFS-style) vs OIDC's JSON tokens; browser-redirect flow with signed XML, SP-initiated or IdP-initiated. One sentence each is enough; nobody expects an Angular dev to configure an IdP.
The line that scores points: "Frontend authorization is UX only — every route and action is re-authorized server-side: JWT verified at the Spring Cloud Gateway, method-level with @PreAuthorize in the services, and data-layer checks. Bypassing the UI still gets a 403." (Mirrors the RBAC bullet in your CV.)
Trap: "CanLoad vs CanMatch?"

CanLoad decided once per session and cached — after logout/login-as-lower-role, the chunk stayed loaded. CanMatch re-evaluates on every navigation match. Always CanMatch on modern Angular.

Trap: "JWT in localStorage — fine?"

Acceptable trade-off in some apps, but XSS then equals token theft. Our pattern: access token in memory only, refresh cookie httpOnly+secure+sameSite, short access-token TTL. Say the threat model out loud — that's the senior version.

Expect a few Quick-fire

  • Java 8→21 features: records (immutable DTOs), sealed interfaces + pattern-matching switch (closed domain events), switch expressions, text blocks, virtual threads (21) — cheap blocking-IO threads; piloting for partner calls, not prod-critical (honest beats bluffing).
  • Streams vs loops: streams for declarative collection transforms; not for everything — readability first; parallelStream uses the common ForkJoin pool.
  • REST versioning (in your CV): URL /v1/ for breaking changes (simple, cacheable, gateway-routable) and header Accept: version=2 for internal clients; deprecation window + Sunset header.
  • GraphQL / gRPC (also in your CV skills — expect a probe): GraphQL = client-shaped queries over one endpoint, kills over-fetching for complex screens; gRPC = HTTP/2 + protobuf contracts, fast internal service-to-service calls with strict schemas; REST stays the public contract — versioned, cacheable, gateway-friendly. "Each has its place" is a safe senior stance.
  • Idempotency in payments: idempotency key on write APIs — first call executes, retries return the same result (ties to the Kafka dedupe answer).
  • Microservices vs monolith: start with a modular monolith; split on scaling/deployment/team boundaries; the cost = distributed tx, tracing, eventual consistency — which is why outbox/sagas exist.
  • Docker/K8s basics: Pod/Deployment/Service/Ingress/HPA; readiness vs liveness (traffic gating vs restart); we deploy via Helm, canary for risky services.
  • SQL tuning: EXPLAIN first; composite index column order (selectivity, leftmost prefix); covering indexes avoid lookups; watch for implicit casts killing index use.
  • Redis patterns: cache-aside + TTL with jitter (no synchronized expiry stampede); evict allkeys-lru vs volatile-lru; use as dedupe/rate-limit counters too.
  • Testing pyramid: many unit (JUnit 5/Mockito) → fewer integration (Testcontainers real Postgres/Kafka) → few E2E (Playwright); 75%+ coverage on critical logic (CV number); contract tests keep microservice APIs honest.
  • Security quick set: OWASP top 3 in our world: injection (parameterized queries/JPA), broken auth (short-lived JWT + refresh rotation), XSS (Angular escaping + CSP); plus CSRF strategy for cookie-based flows, CORS allow-lists at the gateway.

Rehearse 90s each Three STAR stories

Story 1 — Kafka duplicate notifications (the incident story)

Situation: peak-season load → a consumer group rebalance caused event redelivery → customers received duplicate SMS/email notifications.

Task: guarantee single delivery without losing the at-least-once safety net.

Action: event_id dedupe table + Redis TTL cache checked before processing; manual offset commit only after successful processing; cooperative-sticky assignor to reduce rebalances; DLT + alerting for anything still failing.

Result: zero duplicate sends after rollout; consumer-lag alarm tuned on Grafana; the same dedupe pattern got reused by two other teams.

Story 2 — the 40% API performance win (the optimization story)

Situation: transaction-list and reporting endpoints degraded at scale; p95 crept past SLA during peak hours.

Task: cut average API response time without a costly re-platform.

Action: measured first (slow-query log, EXPLAIN, Hibernate statistics) → fixed N+1s with fetch graphs and DTO projections → composite indexes on the hot filters → Redis cache-aside for reference data → batch-write tuning (SEQUENCE ids, JDBC batching).

Result: 40% average response-time reduction; p95 back inside SLA; dashboards added so regressions are caught before users notice.

Story 3 — legacy modernization under load (the fullstack story)

Situation: enterprise app on ASP.NET Web Forms/jQuery — slow to change, no component reuse, hard to hire for.

Task: modernize the frontend to Angular and carve new features into Spring Boot microservices — without stopping the business.

Action: strangler-fig pattern — new screens as Angular 12 feature modules beside legacy pages; reusable component library adopted by other teams; NgRx for cross-module state; guards/interceptors aligned with Spring Security + OAuth2; integrations hardened with retry + circuit breakers.

Result: ~45% faster dashboard loads, a shared design system, and a path off the legacy stack with zero big-bang cutover.
